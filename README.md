# Youreca V2

> **Your Reputation, Your Career**

지인과 함께한 경험을 바탕으로 서로의 평판을 기록하고 확인할 수 있는 서비스 **Youreca**의 재개발 프로젝트입니다.

기존 Youreca는 React와 Firebase를 기반으로 빠르게 서비스를 구축하고 실제 사용자에게 배포·운영했습니다. 약 1년간 서비스를 운영하면서 데이터 구조와 기능 확장 과정에서 여러 한계를 발견했고, 이를 해결하기 위해 서비스의 도메인과 데이터 구조부터 다시 설계하고 있습니다.

V2에서는 단순히 기존 서비스를 새로운 기술로 옮기는 것이 아니라, **실제 서비스를 운영하며 발견한 문제를 바탕으로 더 확장 가능한 구조를 만드는 것**을 목표로 합니다.

이 프로젝트의 고민 사항과 공부 내용 등의 정보들은 모두 기술 블로그에 기록되고 있습니다.

## Why V2?

Youreca V1은 빠르게 서비스를 만들고 실제 사용자에게 제공하는 것을 목표로 개발했습니다.

처음에는 Firebase를 활용해 비교적 빠르게 기능을 구현할 수 있었지만 실제 서비스를 운영하면서 다음과 같은 문제를 발견했습니다.

### 1. 데이터 구조의 한계

초기에는 기능 구현을 우선하면서 데이터 구조를 설계했기 때문에 사용자 정보와 평판 정보가 여러 곳에서 중복되는 문제가 있었습니다.

서비스의 기능이 늘어나면서 동일한 정보를 여러 곳에서 관리해야 하는 상황이 발생했고 데이터 간 관계를 명확하게 표현하기 어려워졌습니다.

### 2. 도메인 관계의 복잡성

Youreca의 핵심 도메인은 단순한 사용자 정보가 아니라,

```text
User
 └── Review
       └── Keyword
```

와 같이 사용자와 평판, 평판과 키워드 사이의 관계를 갖습니다.

특히 한 사용자가 다른 사용자의 평판을 작성하고 하나의 평판에 여러 키워드가 연결되는 구조를 명확하게 모델링할 필요가 있었습니다.

### 3. 기능 확장에 따른 유지보수 문제

초기 구현에서는 하나의 기능을 빠르게 추가하는 것이 쉬웠지만 서비스가 확장되면서 기존 데이터 구조와 새로운 기능 사이의 의존성이 증가했습니다.

따라서 V2에서는 기능을 먼저 구현하기보다 **도메인 관계와 데이터 구조를 먼저 정의하고 이를 기반으로 API와 UI를 설계**하는 방향으로 개발하고 있습니다.

## Goals

V2에서는 다음을 목표로 합니다.

* 기존 서비스에서 발견한 데이터 구조의 문제 개선

* TypeScript를 활용한 명확한 타입 정의
* 서버 상태와 UI 상태의 관심사 분리
* 실제 서비스 확장을 고려한 구조 설계
* 기존 서비스의 기능을 유지하면서 더 나은 개발 경험과 유지보수성 확보

## Domain Model

Youreca의 핵심 도메인은 사용자와 평판입니다.

### User

서비스의 사용자입니다.

```text
User
- id
- nickname
- profileImage
- ...
```

### Review

한 사용자가 다른 사용자에게 작성하는 평판입니다.

```text
Review
- id
- writerId
- targetUserId
- relationship
- visibility
- content
- createdAt
```

### Keyword

평판에서 선택할 수 있는 사전 정의된 키워드입니다.

```text
책임감
성실함
협업
커뮤니케이션
문제해결
빠른 습득
주도적
리더십
배려
긍정적
```

## V1 → V2

Youreca V2는 새로운 서비스를 처음 만드는 프로젝트가 아니라 **실제로 운영했던 서비스의 문제를 발견하고 다시 설계하는 프로젝트**라는 점에 의미가 있습니다.

|           | V1          | V2                            |
| --------- | ----------- | ----------------------------- |
| Framework | React       | Next.js                       |
| Language  | JavaScript  | TypeScript                    |
| Data      | Firebase 중심 | 관계형 데이터 모델                    |
| API       | 기능 중심 구현    | 명확한 Request / Response 설계     |
| Domain    | 기능 구현 중심    | User / Review / Keyword 관계 중심 |
| State     | Firebase 기반 | TanStack Query 기반 서버 상태 관리    |
| Mocking   | -           | MSW                           |
| 목표        | 빠른 서비스 구축   | 확장성과 유지보수성을 고려한 재설계           |

V1에서 실제 사용자에게 서비스를 제공하며 발견한 문제를 V2의 설계에 반영하는 것을 가장 중요한 개발 방향으로 삼고 있습니다.

## Technical Decisions

### Why TypeScript?

V1에서는 JavaScript를 사용하면서 프로젝트 규모가 커질수록 데이터 구조와 API의 형태를 코드만으로 명확하게 파악하기 어려운 상황이 있었습니다.

V2에서는 TypeScript를 사용해 도메인 모델과 API Request / Response를 명시적으로 정의하고, 데이터 구조가 변경될 때 관련 코드에서 문제를 빠르게 발견할 수 있도록 하고 있습니다.

### Why TanStack Query?

서버에서 가져온 데이터와 UI에서 일시적으로 사용하는 상태를 구분하기 위해 서버 상태 관리 도구를 사용합니다.

사용자 정보와 평판 목록과 같은 서버 데이터는 TanStack Query를 통해 관리하고, 폼 입력이나 선택 상태와 같은 UI 상태는 컴포넌트의 로컬 상태로 관리하는 방향으로 설계하고 있습니다.

### Why MSW?

실제 백엔드 API가 완성되기 전에도 프론트엔드 개발을 독립적으로 진행할 수 있도록 MSW를 사용합니다.

이를 통해 실제 API와 유사한 환경에서 Request / Response를 검증하고, 이후 실제 API가 연결되더라도 UI 계층의 변경을 최소화하는 것을 목표로 합니다.

### Why relational data modeling?

V1에서는 Firebase의 구조를 활용해 빠르게 기능을 구현했지만, 실제 서비스 운영 과정에서 User와 Review, Review와 Keyword 사이의 관계가 복잡해졌습니다.

V2에서는 이러한 관계를 먼저 정의한 뒤 데이터 모델과 API를 설계하여 데이터의 중복을 줄이고 기능 확장에 대응할 수 있는 구조를 만드는 것을 목표로 합니다.

## AI-assisted Development

V2 개발 과정에서는 AI를 단순한 코드 생성 도구가 아니라 **설계와 구현을 검증하는 개발 파트너**로 활용하고 있습니다.

현재의 workflow는 다음과 같습니다.

```text
문제 정의
   ↓
요구사항 / 도메인 분석
   ↓
내가 먼저 설계
   ↓
AI에게 다른 접근 방식 질문
   ↓
설계 비교 및 검토
   ↓
직접 구현
   ↓
AI의 제안과 구현 비교
   ↓
테스트 및 검증
   ↓
다음 단계
```

AI가 제안한 코드를 그대로 적용하기보다는 기존 프로젝트의 구조와 컨벤션에 적합한지 직접 검토하고, 실제 동작과 테스트를 통해 검증한 후 적용하고 있습니다.

이를 통해 AI의 생산성을 활용하면서도 최종적인 기술적 판단과 책임은 개발자가 가져가는 것을 중요하게 생각합니다.
